# GASF CRM Workflow Contract (Phase 4 and Phase 5)

Status: **active implementation contract**

This contract defines the completion bars for the remaining workflow hardening
phases after Phase 1 (model/service contract) and Phase 2/3 (operator workflow
integration and queue observability).

---

## Phase 4 — mutation safety and replay resistance

Goal: repeat-submits must not produce duplicate side effects for high-impact
actions.

### 4.1 Required behavior

1. High-impact writes accept a client operation ID (`op_id`) and treat retries
as the same operation.
2. While one operation is in flight, a concurrent duplicate is rejected with a
conflict response.
3. After a successful operation, a duplicate returns success-shaped output
without repeating side effects.
4. On failed operations, the idempotency token is released so a corrected retry
can proceed.

### 4.2 High-impact surfaces in scope

1. Email outbound send actions (`reply`, `forward`).
2. Photo intake/approval actions (`approve`, `invite`, `confirm`, `save`).
3. Destructive or irreversible photo actions (`reject`, held-queue `decide`,
library `delete`, image edit apply/restore).
4. Consent decisions recorded by volunteers (`consent`).

### 4.3 Acceptance criteria

1. Duplicate click/retry cannot send a second outbound email.
2. Duplicate click/retry cannot create duplicate kept photos from one source
attachment.
3. Duplicate click/retry cannot duplicate invite sends, or replay destructive
photo actions.
4. Operation IDs are generated by the UI for covered flows and consumed by the
server.

---

## Phase 5 — controlled rollout and reversible cutover

Goal: keep deployment reversible while preserving one code path for the new
workflow model.

### 5.1 Required behavior

1. Case-workflow surfaces are behind a runtime feature switch.
2. Disabling the switch removes workflow-only UI controls and blocks workflow
REST endpoints with a not-found style response.
3. The legacy inbox/mail path remains usable with the switch off.
4. The switch defaults on for normal operation.

### 5.2 Acceptance criteria

1. A single filter toggles case workflow behavior end-to-end.
2. Queue/case UI is conditionally rendered from the server-side switch state.
3. Workflow-only APIs are inaccessible when disabled.
4. Re-enabling the switch restores queue/case behavior without data migration.

---

## Notes

This contract is intentionally narrow. It defines reliability and rollout
guarantees, not new product behavior.
